# File Ownership

This describes the tier system every project generated by this framework ships with (`harness-core/docs/how-to/file-ownership.md`,
copied verbatim into every project) — reproduced here so a framework contributor can see exactly what a generated
project's owner sees, and understand the contract this repo has to keep honest.

**This repo itself doesn't consume these tiers** — `anyonecan` is the framework source, not a generated project;
nothing here runs `upgrade` against itself. What applies to *this* repo instead: anything under `harness-core/` is
a template, and `harness-core/harness-manifest.json`'s `frameworkOwned`/`languageSpecific` lists decide which of
those template paths become "Framework's" tier for every project that consumes them. Keeping that list accurate is
this repo's job — `scripts/check-sync.mjs` enforces it mechanically (see §3 below), not by convention.

## 1. The three tiers (as a generated project sees them)

### Yours — edit freely, `upgrade` never touches these

`AGENTS.md`, `CLAUDE.md`, `README.md`, `HARNESS-CHANGELOG.md`, all source code, build config, linter config,
`.workspace/STATUS.md`, `.workspace/worklog.md`, `.workspace/plans/*.md` (except `plans/README.md`), `docs/adr/**`,
and the project-specific `*project-rules*` architecture test. Some are seeded once by `setup`/`upgrade` if missing,
then never touched again.

### Framework's — do not edit; `upgrade` overwrites these when unmodified

Exactly `harness-manifest.json`'s `frameworkOwned` + `languageSpecific` sets, reproduced verbatim in the shipped
guide's own Framework tier (`harness-core/docs/how-to/file-ownership.md` §1) — not duplicated here to avoid a
third copy that could drift; see that file for the literal list, or read `harness-core/harness-manifest.json`
directly.

### Customizable, at a cost

Any Framework's-tier file a project deliberately modifies. `upgrade` leaves the project's version alone and offers
the incoming template as `<file>.new` — see the shipped guide's §3 for the exact mechanics (merge cycle, when a
`.new` stops reappearing).

## 2. What this means for developing the framework itself

- Adding a file under `harness-core/.claude/commands/` or `harness-core/docs/how-to/` and forgetting to register
  it in `harness-manifest.json`'s `frameworkOwned` means `upgrade` silently never delivers it to an existing
  project — `check-sync.mjs`'s manifest-registration guard fails the build if you forget (this is what caught the
  1.4.0 near-miss that guard was added for).
- Adding a **new manifest path** whose directory a project might already have written into on its own (e.g. a new
  file under `docs/how-to/` or `scripts/`) is exactly the Homographormer incident this whole file-ownership effort
  traces back to (`.workspace/plans/2026-07-25-file-ownership-rules.md`). The upgrade-tooling fix
  (`.workspace/plans/2026-07-25-upgrade-tooling-safety-and-dry-run.md`) makes this non-destructive — the project's
  file is never overwritten, it gets `.new` treatment — but it still produces a recurring `.new` for that project
  until they either merge to an exact match or relocate their content to `docs/guides/`. Prefer new manifest paths
  under directories a project has no reason to have written into already, when there's a choice.

## 3. Keeping the guide and the manifest from drifting apart

`scripts/check-sync.mjs` fails the build if `harness-core/docs/how-to/file-ownership.md`'s Framework-tier list
(between its `<!-- framework-tier:start -->` / `<!-- framework-tier:end -->` markers) and
`harness-core/harness-manifest.json`'s `frameworkOwned` + every language's `languageSpecific` entries don't match
as sets, in either direction. Run `pnpm validate` (which runs `check-sync`) after touching either file.
